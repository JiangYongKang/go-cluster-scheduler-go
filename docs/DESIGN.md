# 调度语义、资源核算与公平性规则

本文档说明 `scheduler` 包的调度语义、记账不变量、公平性/抢占规则、错误归类，
以及如何在本地验证。所有描述均以内存中的模拟节点为基础，无任何外部依赖。

## 1. 领域模型

- `Resources{CPU, Memory, GPU}`：标量资源向量（每个任务最多申请 1 块 GPU）。
- `NodeSpec`：模拟节点。`NUMA` 为空表示不感知 NUMA；非空时各 NUMA 域的
  CPU/Mem 之和必须等于节点总量，且每块 GPU 必须恰好归属一个域。
- `JobSpec`：作业（作业数组即多个 `TaskSpec`）。携带用户、队列、优先级、
  任务级故障重试上限 `MaxRetries`、亲和性约束。
- `TaskSpec.NUMAID`：`-1` 表示不指定 NUMA 域；`>=0` 表示任务的 CPU/内存与
  GPU（若申请）必须落在该域。`GPUDevice` 非空表示钉选具体 GPU。
- `QuotaConfig.UserWeights` / `QueueWeights`：用户/队列的公平权重（缺省或
  `<=0` 视为 1），仅用于公平份额的归一化，不改变任何配额上限。

## 2. 作业与任务状态机

任务状态：`Pending → Running → Finished`；旁路：
`Running → Preempted →（重新调度）Running`；
`Running/Pending/Preempted → Failed`（取消 `CANCELED`、失联且重试用尽
`RETRIES_EXHAUSTED`）。

作业状态由任务终态聚合：

- 全部 `Finished` → `Finished`；
- 存在 `Failed` → `PartialFailure`（其余任务仍可继续调度/运行）；
- 否则有活动任务 → `Running`；都未启动 → `Pending`；
- `CancelJob` → `Canceled`（终态，不可再调度）。

## 3. 成组调度（gang scheduling）

一次 `Schedule()` 周期对待调度作业按固定顺序逐个处理。对每个作业：

1. 取其**全部**待启动任务（`Pending` 与 `Preempted`，数组维度整体参与）；
2. 做全局运行任务数上限预检；
3. 做用户/队列配额预检（见 §6）；
4. 调用拓扑放置：用带回溯的确定性 DFS 把全部任务作为一个整体装箱到节点。
   仅当每个任务都找到可行放置时才成功；任一任务无解则整组不启动，并汇总
   每个节点被排除的细分原因；
5. 常规放置失败时，尝试整体抢占严格更低优先级作业、以及归一化已消耗份额
   严格更大的同优先级作业（见 §7）；
6. 抢占结算完成后，整组任务在一次原子提交中启动（见 §8）。

因此在资源不足时**绝不会出现部分任务启动**。

放置确定性来自：节点排序（软亲和得分降序 → 节点名升序）、任务排序
（约束严格度：钉 GPU > 钉 NUMA > 申请 GPU > 需求降序 > 任务名升序）、
GPU/NUMA 选择按 ID 升序。相同输入序列产生相同结果。

## 4. 拓扑约束与可区分原因

`filterNode` 对每个 (节点, 任务) 评估并返回全部违反项（不去除候选以外的
信息，仅用于判定与解释）：

| 原因码 | 含义 |
|---|---|
| `NODE_NOT_READY` | 节点处于 Drained/Lost |
| `LABEL_MISMATCH` | 硬亲和标签不相等或命中 NoScheduleKeys |
| `ANTI_AFFINITY` | 反亲和作业仍在该节点运行（拟抢占移除的除外） |
| `CPU_INSUFFICIENT` / `MEMORY_INSUFFICIENT` | 节点总量不足 |
| `GPU_ABSENT` | 设备在该节点上根本不存在 |
| `GPU_BUSY` | 设备存在但已被占用（钉设备、同作业累计占用、同域占用） |
| `GPU_ZONE_MISMATCH` | 钉选设备存在，但不属于指定的资源域（NUMA 域） |
| `NUMA_ZONE_ABSENT` / `NUMA_ZONE_EXHAUSTED` | 域不存在 / 域内 CPU 或内存不足 |
| `NODE_TASK_CAP` | 超过节点 `MaxTasks` |

**设备绑定与资源域的严格一致性：**

- 钉选设备（`GPUDevice != ""`）的任务，最终运行时必须真的落在该设备上；
  设备不存在给 `GPU_ABSENT`、被占用给 `GPU_BUSY`，两类原因互不混淆。
  **该规则在平铺（`NUMA` 为空、无资源域）节点上同样成立**：钉哪块卡就落哪
  块卡，即使同节点上存在编号更靠前的空闲卡也绝不改选；设备不存在或已占用时
  该节点直接排除，不回退到同节点其它卡。
- 同时指定资源域时，设备必须恰好属于该域，否则给 `GPU_ZONE_MISMATCH`；
  **绝不**退回同节点的其它设备或别的域。平铺节点没有资源域概念，因此
  不会出现 `GPU_ZONE_MISMATCH`（三种情形因此可清晰区分：无域节点只有
  `GPU_ABSENT` / `GPU_BUSY`；有域节点才可能 `GPU_ZONE_MISMATCH`）。
- 在感知 NUMA 的节点上即使没有显式指定域，钉设备任务的 CPU、内存与 GPU
  也必须同落在设备的归属域；归属域 CPU/内存不足给 `NUMA_ZONE_EXHAUSTED`，
  不会借另一域的 CPU/内存运行。
- 未钉设备、仅申请 GPU 时，只能在满足 CPU/内存的域内选一块空闲卡。

硬约束（标签、反亲和、设备缺失、设备跨域、域缺失）**不会**因抢占而变得可满足；
容量类约束（CPU/Mem/GPU 忙/域耗尽/任务上限）才可能通过抢占腾出。
调度器绝不把任务放到违反其硬约束的节点上（无静默降级）。

最终对作业的拒绝原因归类：

- `CONSTRAINT_CONFLICT`：即使移除全部可抢占任务，剩下的仍是纯硬约束违反；
- `PREEMPTION_NOT_ENOUGH`：存在容量类违反，但把可抢占对象（严格更低优先级 +
  份额严格更大的同优先级运行作业）全部移除后仍放不下；
- `NO_YIELDABLE_SHARE`：容量被占满但占用者中没有任何可让出对象——同优先级
  运行者的归一化已消耗份额都不大于本作业（相等或更小），且更低优先级腾完
  仍不够；维持原状，无人被抢；
- `QUOTA_EXCEEDED`：用户/队列配额不允许新增份额；
- `RUNNING_TASK_LIMIT` / `PENDING_LIMIT` / `QUEUE_FULL`：规模上限；
- `NO_CANDIDATE_NODES`：集群没有任何已注册节点。

## 5. 调度排序与公平共享

待调度作业顺序：

1. **优先级降序**（数值越大越优先）；
2. 同优先级按用户**归一化持有份额升序**：
   `share = (CPU + Memory/1024 + GPU*1024) / 用户权重`，作用于该用户的
   `allocated`（运行 + 预留）；权重取自 `QuotaConfig.UserWeights`，缺省为 1；
3. 再按提交序号升序、作业 ID 升序。

预留份额计入归一化持有份额，避免“被抢占越多反而越优先”的作弊；这里用的是
**瞬时持有份额**而非历史累计消耗：被抢占作业的累计消耗在其重启时不会使它的
持有份额变大，因此它在胜出者释放资源后会自然回到队首重新调度，不会因为历史
上被抢过、剩余份额少就一直被压着起不来。

### 5.1 同优先级抢占的受害者公平

从本版起，同优先级作业之间**允许**基于“已消耗资源份额”的单向抢占，
严格高优先级可抢占低优先级的既有规则保持不变：

- 抢占候选优先级规则：严格更低优先级作业始终可被抢占（同 §7）；
  **同优先级**作业只有在其归一化已消耗份额**严格更大**时才可被让出。
- 归一化已消耗份额按作业到调度时刻为止累计消耗掉的资源份额计算：
  `consumed = rtValue(该作业全部任务各运行时段资源时间之和) /
  (用户权重 × 队列权重)`；
- 当前仍在运行的时段按 `startedAt..now` 即时计入；被抢占后重启的任务，其
  重启后的时段与此前各段**按段累加**，重复抢占不重复记也不漏记
  （与 §6 的资源时间同一套分段账本）；
- 消耗（权重归一化后）**严格越大**的作业越先被让出，因此长期占资源、累计
  消耗最多的作业不再“最安全”；新来者份额为 0（更小）可以顶掉长跑多耗者；
  **消耗相等或更小的一方不得被抢**（严格大于，不接受相等），消耗量相同时
  维持原状，不引入按 ID 或提交序的同优先级抢占。
- 一个调度周期内候选的贪心加入顺序仍是“优先级升序 → 同优先级内归一化
  已消耗份额降序 → 作业 ID 升序（仅用于同份额的确定性展示）”，找到可行
  集合后同样做最小化剪枝（§7）。
- 当更低优先级全部腾完仍放不下，且不存在任何份额严格更大的同优先级运行
  作业时，作业本周期维持原状并以可区分原因
  `NO_YIELDABLE_SHARE` 拒绝（区别于 `PREEMPTION_NOT_ENOUGH`）。

注意被抢占任务此前的被抢时段虽然计入其历史消耗，但它重新参与调度时依据的是
持有份额排序（§5 第 2 条），不会被历史消耗永久压制：胜出者释放资源后，被抢
作业会自然回到队首重新调度。被抢作业重排队时若与运行者份额相等（例如双方都
刚结算过相同时长），则本轮谁也不让，等任一方的相对份额发生变化后再判定。

## 6. 资源核算与配额

全部份额变更集中在 `accounting.go` / `lifecycle.go`，在单一互斥锁内完成。

**两类份额：**

- 运行份额（`userUsed`/`queueUsed` 与各节点账本）：任务运行期间持有；
- 预留份额（`preemptHold`，按 `jobID/taskName` 去重）：任务被抢占或节点
  失联待重试期间持有，代表“仍属于该用户/队列、稍后要回来”的额度。

**不变量：**

1. 每个运行中任务恰有一份运行份额；每个待恢复任务恰有一份预留份额。
2. `allocated = running + held`；抢占只是把份额在两类之间搬运，
   **不改变任何用户/队列的 allocated 总量**，因此抢占无法绕过配额。
3. 节点账本（已用 CPU/Mem、忙 GPU 集合、NUMA 域占用、任务计数）与其
   `running` 任务集合严格一一对应；提交/回滚/完成/抢占/失联路径对称。
4. 提交时按“作业全部任务资源 + 当前 allocated”做配额与队列授权校验；
   调度时按“新增（非预留转换）份额 + 当前 allocated”再次预检。
5. 被抢占任务重新启动走 `held → running`（allocated 不变）；被取消或重试用尽
   时释放预留（allocated 减少）。

失败路径（配额拒绝、放置后提交失败、抢占后仍无法启动）都不会写入半截状态：
任务整组启动使用先落账、失败逆序回滚（节点占用、运行/预留份额、任务态）。

### 6.1 累计资源时间视角（ResourceTimes）

除瞬时占用（`Snapshot`）外，调度器在每个任务上维护按终局原因分桶的**资源
时间**（资源 × 时长，CPU/内存/GPU 各一维，纳秒记账）。通过
`Scheduler.ResourceTimes()` 可一次性拿到用户、队列、作业三个维度的报表：

- 五个桶：`Running`（当前在跑的未结时段，按查询时刻即时结算）、
  `Finished`（正常结束）、`Canceled`（被取消）、`Failed`（失败：失联且
  重试用尽等）、`Preempted`（被抢占的已结时段）。
- 恒等式：**Running + Finished + Canceled + Failed + Preempted = Total**，
  在用户、队列、作业三个维度上分别成立。
- 记账点只有运行时段结算处（完成、抢占、取消、失联），每段运行时间在结算
  时进入且仅进入一个桶；当前运行段不提前入账，查询时才按
  `startedAt..now` 计入 Running，因此抢占回补、重启、取消、失败重试的任意
  组合都不会让同一段时间被记两次或漏记。
- 被抢占任务其后重启：被抢段留在 `Preempted`，重启后到下一次终局的时段按
  当时原因（如完成进 `Finished`）另行累计，多段相加即总量。同优先级抢占
  与高优先级抢占走同一套结算路径，分段记账语义完全一致。
- 查询与 `Submit/Schedule/CancelJob/Tick/SetNodeState` 共用同一把互斥锁，
  并在读临界区内一次性聚合，故并发进行时读出来的仍是某个一致时刻的自洽视图。

### 6.2 与既有行为的兼容范围

本次调整只改变两点，其余语义全部保持：

- **变化 1**：同优先级作业之间从“互不抢占”改为“归一化已消耗份额严格更大
  才可被抢”；严格高优先级抢低优先级、成组调度、配额预检、最小化剪枝、
  被抢后重启与份额搬运规则均不变。份额相等的同优先级作业对之间行为与旧版
  一致（维持原状），只是拒绝原因从 `PREEMPTION_NOT_ENOUGH` 细化为
  `NO_YIELDABLE_SHARE`。
- **变化 2**：平铺（无资源域）节点上的钉设备从“可能静默改选编号最小的空闲
  卡”改为“必须落在指定卡”；无资源域节点不存在域概念，因此不会新增
  `GPU_ZONE_MISMATCH`，既有 NUMA 节点的钉设备/同域校验结果不变。
- 节点失联恢复、失败重试、取消、决策日志、确定性放置与并发模型均未改动。

## 7. 抢占规则

- 可抢占对象有两类，均要求其仍有运行中任务、且作业未终态：
  1. 优先级**严格小于**胜出者的作业（既有语义，保持不变）；
  2. 优先级**相同**、且到调度时刻为止的归一化已消耗份额
     **严格大于**胜出者的作业（`consumed(v) > consumed(j)`，见 §5.1）。
     份额相等或更小者不得被抢：消耗更少的运行者不能被消耗更多的一方抢走，
     新来的零消耗者可以顶掉长跑多耗者。
  严格更高优先级作业在任何情况下都不可抢占。
- 候选受害者按“优先级升序 → 同优先级内归一化已消耗份额降序 →
  作业 ID 升序”贪心加入；每加入一个作业即在“移除其全部运行任务”的预演
  视图上尝试整体放置。
- 可行性判定用两组预演区分拒绝原因：仅移除“可让出者”后可行则进入最小化；
  连所有优先级不高于胜出者的运行作业（含不可让出的同优先级者）都移除仍不
  可行，按 §4 归类为 `PREEMPTION_NOT_ENOUGH` / `CONSTRAINT_CONFLICT`；
  理论上限可行、但可让出集合不足（同优先级无人份额严格更大）则给
  `NO_YIELDABLE_SHARE`，维持原状。
- 找到可行集合后，按加入逆序做**最小化剪枝**：能移除的受害者一律移除，避免
  过度抢占；最终再放置一次得到对应计划。
- 抢占在胜出者启动**之前**结算：每个受害者任务
  - 计算自上次启动以来的运行时段并累加到任务的累计运行时；
  - 从节点 `running` 与节点账本摘除；
  - 用户/队列运行份额回补，并登记同量预留；
  - 状态置 `Preempted`。
- 多次抢占（含同优先级）：每次只结算当前运行时段，累计运行时为各段之和；
  同一任务的预留份额始终只有一份，重复抢占幂等，不重复计入也不丢失。
- 抢占尝试失败（无可让出者，或最大范围抢占仍放不下）时，不会触动任何受害者。
- 与配额的关系不变：抢占只在运行份额与预留份额之间搬运，不改变任何用户/
  队列的 allocated 总量，因此同优先级抢占同样无法绕过配额（§6）。

## 8. 原子整组提交

`startTasks` 对待启动任务依次：预留转运行或新计入份额 → 写节点账本与
`running` 集合 → 置 `Running`、记录节点/GPU/NUMA/启动时刻。任一步失败则
逆序撤销此前全部变更（已在节点上的占用、份额、任务态），返回带原因码错误，
保证无半更新状态。

## 9. 节点故障与恢复

`SetNodeState(name, NodeLost)` 在锁内原子地：

- 把该节点全部运行任务按 key 排序后逐个摘除、结算运行时段；
- 任务 `retries < MaxRetries`：`retries++`，置回 `Pending`，节点占用回补、
  登记同量预留，等待下一周期重新调度（记 `TASK_RETRY`）；
- 否则置 `Failed / RETRIES_EXHAUSTED` 并释放份额（可区分终态，记
  `RETRY_EXHAUSTED`）；
- 节点账本整体清零；失联期间其状态非 Ready，放置器直接排除，因此任务不可能
  同时记账在两个节点上。
- 节点恢复为 `Ready` 后从空账本重新接受新任务；已在其他节点重跑的任务不会
  自动回迁。

## 10. 并发模型与规模上限

- 单个 `sync.Mutex` 保护全部可变状态；`Submit/Schedule/CancelJob/Tick/
  SetNodeState/Snapshot/GetJob/Decisions` 均为串行化临界区。
- 时钟为显式模拟时钟：`SetClock` 设定原点，`Tick` 推进并完成给定任务，
  `Schedule` 使用当前时钟标记启动时刻。
- 上限配置：`MaxPendingJobs`（待调度作业总数）、`QueueMaxPending`、
  `MaxRunningTasks`（全局运行任务数）、`QuotaConfig.MaxJobsTotal`、
  `MaxDecisionLog`（决策日志保留条数；超限丢弃最旧记录）。超限按原因码拒绝
  或留待后续周期，内存占用有界。

## 11. 决策日志与可解释性

每次提交/拒绝/启动/抢占/完成/取消/失联/重试都追加一条 `Decision`，包含时间、
类型、作业、任务、节点、原因码与详情。测试中统一在用例开始打印调度输入、
在判定处打印原因（`go test -v` 可见）。`ScheduleReport` 还会直接返回本周期
启动的作业/任务、抢占结算记录（含已结运行时与回补份额）、不可调度作业及每
节点细分原因。

## 12. 本地验证方法

```bash
# 全部单测（覆盖资源不足、约束冲突、抢占、故障、配额、取消、并发）
go test ./...

# 竞态检测
go test -race ./...

# 查看每个用例打印的“输入 + 判定依据”
go test ./scheduler/ -v

# 端到端演示（GPU/NUMA、成组、抢占、失联、恢复、取消、核算快照）
go run ./cmd/sim
```

测试文件与场景对应：

| 文件 | 覆盖场景 |
|---|---|
| `gang_test.go` | 成组调度、资源不足不部分启动、跨节点装箱 |
| `topology_test.go` | GPU 钉选不降级、NUMA 域缺失/耗尽、硬亲和、反亲和 |
| `binding_test.go` | 钉设备不存在/被占用/跨域原因可区分、钉设备未指定域时 CPU/内存同域不回退、落账正确；平铺（无资源域）节点钉设备同样不回退 |
| `preempt_test.go` | 抢占结算、份额回补/预留守恒、重启、份额相等同优先级不抢占（`NO_YIELDABLE_SHARE`）、多次抢占 |
| `fairpreempt_test.go` | 低优先级受害者按归一化已消耗份额选择、权重归一化、被抢后能重启、多轮抢占分段累加 |
| `samepripreempt_test.go` | 同优先级长跑被零消耗新来者顶掉、反向抢不动、份额相等无人可让、权重归一化两个方向 |
| `samepriconservation_test.go` | 同优先级抢占→重启→再抢→完成/取消/失联失败重试的跨阶段分段累加与五桶守恒、并发读自洽 |
| `resourcetime_test.go` | 五桶之和=总量；抢占重启、取消、失败重试跨阶段守恒；并发读自洽 |
| `failure_test.go` | 失联摘除与重试、重试耗尽终态、节点恢复、运行时结算、无双开记账 |
| `quota_test.go` | 取消守恒、用户/队列配额原子拒绝、队列授权、规模上限、抢占不绕过配额 |
| `concurrency_test.go` | 并发安全（-race）、同序列结果可复现、决策日志有界、重复提交拒绝 |
